### SOCK-1: Add GET /catalogue/{id}/stock route returning a product's units in stock
Problem: The product page needs to know how many units of a product remain so it can show a low stock badge when fewer than 5 are left. The catalogue service has no route that returns stock for one product. The wiki lists only GET /catalogue, /catalogue/size, /catalogue/{id}, /tags, /catalogue/images/*, /health and /metrics.

Approach: Follow the service's existing go-kit layering.
(1) service.go: add a Stock(id string) (int, error) method to the Service interface and its implementation. It runs a parameterized single-row SELECT through sqlx against the sock table, the same way Service.Get does, and returns ErrNotFound when no row matches.
(2) endpoints.go: add a stockRequest and stockResponse with OpenTracing, following the existing Get endpoint. The span name is 'GET /catalogue/{id}/stock'.
(3) transport.go: register GET /catalogue/{id}/stock on the gorilla/mux router. Read the id with mux.Vars. Encode the response as JSON {"id": "<id>", "stock": <int>}. Map ErrNotFound to 404 and database errors to 500, as encodeGetResponse does. Put the route under the existing circuit breaker.
(4) logging.go: add Stock to LoggingMiddleware, logging the id, result and elapsed time.

The stock column is unclear. The wiki does not describe the sock table schema. If a quantity column already exists in socksdb, use it. If not, a schema and seed-data change to catalogue-db is needed (see open questions). The route is read-only, so the service stays read-only. The response returns the raw count only. The low stock threshold (5) belongs to the front-end and is not encoded here.

Out of scope: stock reservation or decrement on purchase, write endpoints, auth, and changes to the GET /catalogue or GET /catalogue/{id} response shapes.
Acceptance criteria:
- Given a product with id X exists in socksdb with 3 units in stock, when a client calls GET /catalogue/X/stock, then the service returns HTTP 200 with Content-Type application/json and body {"id":"X","stock":3}
- Given no product with id Y exists, when a client calls GET /catalogue/Y/stock, then the service returns HTTP 404, using the same error-to-status mapping as GET /catalogue/{id}
- Given the catalogue-db connection is unavailable, when a client calls GET /catalogue/X/stock, then the service returns HTTP 500 and does not panic, and GET /health reports catalogue-db as err
- Given the new route is registered in transport.go, when clients call GET /catalogue/size, GET /catalogue/X and GET /catalogue, then each returns the same status and body shape as before the change (the new route does not shadow or break existing routes)
- Given a request to GET /catalogue/X/stock has completed, when an operator checks the stderr logs and GET /metrics, then LoggingMiddleware has logged method=Stock with the id, result and elapsed time, and the HTTPLatency histogram has a sample for the stock path
