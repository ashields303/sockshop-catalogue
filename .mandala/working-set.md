### CAT-1: Paginate the catalogue listing
The listing returns every item in one response and takes seconds to render. Page it at 50 items with next and previous links.
Acceptance criteria:
- Given a catalogue with 500 items, when GET /catalogue is requested without a page parameter, then 50 items are returned along with a link to page 2
Test notes:
- (unit) In the catalogue service, test the pagination logic in isolation: seed a mock database with 500 items, call the listing handler with no page param, and assert exactly 50 items are returned and the next-page link points to page 2.
- (unit) Test boundary conditions: last page returns fewer than 50 items and no next-page link; page 1 returns no previous-page link; requesting a page beyond the last page returns an empty list or a 404.
- (integration) Spin up the catalogue service with a real MySQL (socksdb) database seeded with 500 rows. Issue GET /catalogue, GET /catalogue?page=2, and GET /catalogue?page=10 and assert correct item counts and correct next/previous link values in each response.
- (integration) Verify GET /catalogue/size still returns the total count (500) regardless of pagination, so the front-end can compute total pages.
- (manual) In a running Sock Shop environment, open the front-end catalogue page and confirm that only 50 socks appear on the first page, a 'next' link is visible, clicking it loads page 2, and a 'previous' link appears on page 2.
- (manual) Confirm that tag-based filtering (GET /catalogue?tags=<tag>) combined with pagination returns the correct subset of items split across pages, and that the next/previous links preserve the tag query parameter.
