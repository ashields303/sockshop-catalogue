### CAT-1: Show low-stock badge on product tiles
**As a** shopper browsing the catalogue, **I want** to see a low-stock badge on product tiles when stock is running low, **so that** I can make faster purchasing decisions before an item sells out.

**Context:** The catalogue service (`ashields303/sockshop-catalogue`) exposes `GET /catalogue` and `GET /catalogue/{id}` and is consumed by the front-end for product browsing. Currently no stock-level signal is surfaced to the shopper on listing pages.

**Scope:**
- Add a `low_stock` boolean (or equivalent threshold field) to the catalogue API response.
- Render a visible badge on product tiles in the front-end when `low_stock` is true.
- Threshold value (e.g. quantity ≤ 10) to be agreed with product; treat as a configurable constant for now.

**Out of scope:** Real-time inventory updates, cart reservation, stock management UI.

**Notes for developers:** The catalogue service is read-only Go + MySQL (`socksdb`). Any stock quantity field must already exist in the DB schema or be added via migration. Front-end proxies `/catalogue*` routes directly.
Acceptance criteria:
- Given A sock product has a stock quantity at or below the configured low-stock threshold, when The front-end calls `GET /catalogue` or `GET /catalogue/{id}`, then The catalogue service response includes a `low_stock: true` field for that product
- Given A sock product has a stock quantity above the configured low-stock threshold, when The front-end calls `GET /catalogue` or `GET /catalogue/{id}`, then The catalogue service response includes `low_stock: false` for that product, and no badge is shown
- Given The catalogue API returns `low_stock: true` for a product, when A shopper views the product tile on the catalogue listing page, then A clearly visible 'Low Stock' badge is rendered on that product tile
- Given The low-stock threshold is set to a configurable constant, when A developer changes the threshold value and restarts the service, then Products are classified as low-stock or not according to the new threshold, with no code change required beyond the configuration
- Given The catalogue service is running and connected to `catalogue-db:3306`, when A health check is performed via `GET /health`, then The service reports healthy, confirming no regression was introduced by the stock-field addition
Test notes:
- (unit) In the Go catalogue service, unit-test the function or method that maps a product's stock quantity to the `low_stock` boolean, covering: quantity == threshold (boundary, expected true), quantity == threshold + 1 (false), quantity == 0 (true), quantity well above threshold (false).
- (integration) Spin up the catalogue service with a test MySQL instance (`socksdb`). Seed products with quantities above, at, and below the threshold. Assert that `GET /catalogue` and `GET /catalogue/{id}` return correct `low_stock` values for each case.
- (integration) Confirm `GET /health` still returns 200 OK after the schema/model change, ensuring the DB connection and query path are unbroken.
- (e2e) In a full Sock Shop stack, navigate to the catalogue listing page. Verify a product seeded with stock ≤ threshold displays the 'Low Stock' badge, and a product with stock above threshold does not. Check on both the listing grid (`GET /catalogue`) and the detail view (`GET /catalogue/{id}`).
- (manual) Change the low-stock threshold config value, restart only the catalogue service, and reload the front-end. Confirm that badge visibility changes accordingly without a code redeploy.
- (manual) Visually inspect the badge on the product tile at multiple viewport sizes (mobile, tablet, desktop) to confirm it does not obscure the product image, name, or price.
