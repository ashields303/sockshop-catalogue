Status: all five tickets are implemented and every acceptance criterion is met. Each criterion is covered by Go unit tests (`go test` in `golang:1.7`, the CI toolchain: 23 tests, all passing). I also checked every criterion by hand against the real service binary and a MySQL 5.7 container loaded from `docker/catalogue-db/data/dump.sql`. `make test` was not run as a whole (see below).

- **SOCK-6, schema.** `sock.count` already existed but was nullable. In `dump.sql` it is now `INT NOT NULL DEFAULT 0` with `CHECK (count >= 0)`, and the new `stock_adjustments` table has an `ENUM` reason, a foreign key to `sock` and an index on `(sock_id, created_at DESC)`. On MySQL 5.7: inserting a row with reason `gift` fails (strict mode, error 1265), an unknown `sock_id` fails on the foreign key (error 1452), and the index exists. There was no migration tool, so `docker/catalogue-db/migrations/001_stock_adjustments.sql` brings an existing database up to date. I applied it to a database built from the old dump: every seed row was unchanged, and a row with a NULL count became 0. **Caveat:** MySQL 5.7 reads `CHECK` but does not enforce it (8.0.16+ does). The `catalogue-db` image is `mysql:5.7`, so on 5.7 the non-negative rule is enforced by `AdjustStock`, not by the database. MySQL 5.7 also ignores `DESC` in index definitions. The index is still used for the history query. The `StockAdjustment` model is next to `Sock` in `service.go`.
- **SOCK-7, PATCH.** `AdjustStock` runs BEGIN, `SELECT ... FOR UPDATE`, UPDATE, INSERT, COMMIT in one transaction, and rolls back with no writes on not-found or insufficient stock. Errors map to responses in `encodeError`: 404, 409 (`ErrInsufficientStock`) and 400 (`ErrInvalidReason`, `ErrInvalidDelta`, and `ErrMalformedBody` for bad JSON or a non-integer delta). Live check: 20 rounds of two parallel `-1` requests on stock 1. Every round gave exactly one 200 and one 409, and stock ended at 0. GET `/catalogue`, `/catalogue/size`, `/catalogue/{id}` and `/catalogue/{id}/stock` respond as before.
- **Change to the circuit breaker (applies to all three new routes).** Endpoints return client errors (not found, invalid input, insufficient stock) inside the response, not as endpoint errors. Otherwise gobreaker opens after 5 consecutive failures, and a short run of 409s would turn every adjustment into a 500 for 30 seconds. A mutation test confirmed this: without the change, the 7th conflict returned 500. `TestTransportAdjustStockConflictsDoNotTripBreaker` checks it. Database errors still count towards the breaker. The existing GET routes are unchanged.
- **SOCK-8, history.** The query has `ORDER BY created_at DESC, id DESC LIMIT 50`. The `id` tie-break matters because `created_at` has one-second resolution, so several adjustments in the same second would otherwise come back in arbitrary order. `created_at` is read as `UNIX_TIMESTAMP(...)`. The DSN has no `parseTime`, and this way the RFC3339 UTC timestamp does not depend on the session time zone. Live check: after 60 adjustments, exactly 50 came back, newest first. Three adjustments matched the stored rows. A product with no adjustments returned `200 []`, and an unknown id returned 404.
- **SOCK-9, audit.** `StockAuditMiddleware` in `logging.go` is a decorator. It logs `event=stock_adjusted id delta reason new_count` and increments `catalogue_stock_adjustments_total{reason}` only after a committed adjustment. The counter is registered next to `HTTPLatency` in `main.go`. All four reasons are set to 0 at startup. The vendored `client_golang` predates `testutil`, so the tests read the counter through `client_model` instead of `testutil.ToFloat64`. Live check: `/metrics` showed four zeros at start, sale went up by exactly 1 after one adjustment, and the 409 and 400 responses changed nothing. There was exactly one `event=stock_adjusted` log line.
